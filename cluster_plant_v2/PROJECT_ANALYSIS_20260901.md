# Cluster Plant V2 — 项目结构与现状分析报告

分析日期：2026-09-01
分析范围：`cluster_plant_v2/` 全目录（含 `thermal/`、`control/`、`tests/`、`validation/`、`model_data/`）
代码规模：约 6,974 行 Python（运行时 + 测试），27 个验证脚本，49 个结果目录

---

## 1. 一句话定位

这是一个**五 Pack 电池簇储能热管理系统的高保真仿真工厂 + 非线性模型预测控制（NMPC）验证平台**。

它回答一个工程问题：*当 5 个 280 Ah 电池包以 AGC 调频工况（RegD）剧烈发热时，如何用最省的电把电芯温度死死摁在 25 °C 附近？*

整套系统采用**双模型架构**——高保真 Plant 当"真实现实"，冻结降阶模型当"控制器脑内世界"，两者通过适配器对话。这是工业 MPC 的标准范式，在这里被实现得相当彻底。

---

## 2. 物理链路：一个 9 步闭环

`plant.py` 中的 `ClusterPlant.step()` 是整个系统的心脏，推进顺序被显式固定（5 s 定步长）：

```
水箱 → 泵 → 并联母管水力网络 → 压缩机执行器 → R134a 制冷循环
     → 蒸发器动态 → 15 s 供液延迟 → 5-Pack 电池簇 → 20 s 回液延迟 → 水箱 → 诊断
```

| 环节 | 模块 | 物理内容 |
|---|---|---|
| 电池产热 | `thermal/pack_rom.py` | 4×3 分区降阶 ROM，HPPC 冻结参数表（R0/R1/R2 随 SOC、温度查表），2RC 极化，4 支路并联分流 |
| 冷板换热 | `thermal/cold_plate_rom.py` | 13 节点冷板 → 3 区降阶，LMTD 稳健换热 |
| 单体耦合 | `thermal/reduced_pack.py` | 电池 ROM + 冷板 ROM 能量守恒耦合 |
| 簇级组织 | `thermal/cluster.py` | 5 Pack 并联分流、回液质量加权混合、Pack 间温差统计 |
| 水力网络 | `hydraulics.py` | 并联母管阻力网络、泵相似定律（1600–4800 rpm）、3 L 水箱混合 |
| 制冷循环 | `refrigeration.py` | **CoolProp 真实 R134a 物性**，5×5 压缩机效率图谱插值，ε-NTU 蒸发器/冷凝器，三残差 `least_squares` 联立求解 |

### 关键设计亮点

**① 制冷循环是真解方程，不是查表**
`ClosedR134aCycle.solve()` 以（蒸发温度、冷凝温度、制冷剂流量）为未知量，联立三个归一化残差（质量流量闭合、蒸发器能量、冷凝器能量），用 `scipy.least_squares` 收敛到 `xtol=1e-11`。物性全部走 CoolProp。这意味着模型具备**外推能力**——超出标定工况仍有物理意义。

**② 能量守恒被当作一等公民**
每一步都输出一串残差诊断：`cycle_energy_residual_w`、`cluster_fluid_residual_w`、`tank_energy_residual_j`、`evaporator_dynamic_energy_residual_j`。这种"处处留痕"的审计习惯在仿真项目里相当罕见，也是这个项目能放心做参数缩放的底气。

**③ 数值失效的优雅降级**
低负荷下回液过冷会让蒸发温度跌破 7 °C 下限、循环无物理解。代码按 0.9→0.2 几何降速重试，模拟真实机组的压缩机卸载逻辑，而不是简单抛异常。另有 `COMPRESSOR_SPINUP_SPEED_RPM = 900` 处理停机重启时的转速爬升死区。

## 3. 控制层：两代并存

`control/` 目录里躺着**两代控制器**，这是一个需要清理的现状：

| 代数 | 文件 | 状态 |
|---|---|---|
| 第一代 | `cluster_domp_model.py` + `cluster_domp_mpc.py` + `chiller_surrogates.py` | 自建降阶模型（集中参数热链 + 二次响应曲面代理制冷能力），**已被取代但仍在库内** |
| 第二代（现役） | `physics_p_nmpc_model.py` + `physics_p_nmpc_controller.py` | 基于冻结的 Physics-P 工件，do-mpc 5.x + CasADi + IPOPT 直接解非线性 NLP |

### 现役 NMPC 规格

- **状态维度 16** = 14 物理状态（`t_bat, t_tank, t_plate, n_comp, n_pump, q_evap, z_pump, z_supply[1:3], z_return[1:4]`）+ 2 个增广状态（上一条指令，用于表达 Δu 约束）
- **控制量 2**：压缩机转速指令、泵转速指令
- **时变扰动 3**：电流、环境温度、**产热功率预览**（SOC 感知，用 HPPC 表做库仑计数滚动预测）
- **预测域 300 s**（60 步 × 5 s），每 15 s 重优化一次，中间两步保持指令
- **目标函数**：非对称温度带惩罚（`w_upper = w_lower = 5000` 远高于 `w_track = 500`）+ 三次方能耗项 + Δu 平滑项
- **硬约束**：Δu 通过增广状态以 `set_nl_cons` 成对表达（`set_nl_cons` 只支持单侧上界，故写成上下两式）

### 一个巧妙又危险的工程补丁

`ClusterCasadiPhysicsP` 覆写了父类的 `_build_function()`，把单 Pack 标定的冻结模型改造成 5 Pack 部署形态：每个 Pack 只看到 1/5 流量，但 N 个 Pack 的板换热量共同加热回液管。这个修正把 Pack-流体换热导从 545 W/K 拉到约 390 W/K，消除了闭环约 1.2 K 的稳态偏差。

**代价**：绕过了单 Pack 时代的冻结工件校验器。父类校验仍在跑，但它只约束一个已被新结构弃用的 `plate_fluid_effectiveness` 字段——也就是说，**这道防线现在形同虚设**。

## 4. 验证体系：规模可观

```
tests/          19 个单元测试文件       → 155 个用例，全部通过（57.5 s）
validation/     27 个验证脚本 + 15 个契约测试 + 4 个可复用回归循环
results/        49 个归档结果目录（时序 CSV + 对比图 + 汇总 JSON）
```

分级验证的痕迹清晰可循：Stage 6 → 7a → 7b → 8a → 8b → 8c1 → 8D2 → 8D3 → 8D4（含 8D4b/c/d/e/f/j 子阶段）。每次参数改动后都跑既有的回归测试，这个纪律值得肯定。

### NMPC 实测收益（600 s 闭环，对比固定 4000/3600 rpm 基线）

| 工况 | 基线 | Physics-P NMPC |
|---|---|---|
| S0 恒流 560 A | 25.15 °C / 0.1483 kWh | 25.18 °C / **0.1351 kWh（−8.9%）** |
| S1 阶跃至 1120 A | 带误差 2.184 K | **2.146 K**（能耗 +71%，抗大阶跃的合理代价） |
| T2 PJM RegD | 24.44 °C（过冷）/ 0.1483 kWh | **25.08 °C / 0.0890 kWh（−40%）** |

求解耗时 0.18–4.95 s/次，满足 15 s 控制周期，实时性有余量。

## 5. 最新动态：正在向真实设备靠拢

`model_data/real_data_anchors/`（今日 2026-09-01 刚建）标志着项目从"理论自洽"迈向"实测标定"：

- Jilipow 液冷电池柜规格书原件 PDF + 文字提取
- R134a 压缩机样本点 12 条、储能液冷整机额定点 5 条、系统级实测点 10 条
- 热物性锚点对照表 13 项

**已发现的保真度缺口**：当前 8D4 冻结配置（72 cc 压缩机）模型轴端 COP 为 4000 rpm ≈ 3.98、6000 rpm ≈ 3.36（工况 A：进水 18 °C / 环境 45 °C），而真实整机 COP 只有 **1.56~2.76**。

通过 CoolProp 反算 Boyard JVSB150Z24 样本工况点得 η_vol = 0.887、η_is×η_motor = 0.641，与模型 5×5 效率图在相近压比处的取值方向一致。

> **重要修正**：本节初稿曾判定"模型 COP 高估约 1.5 倍"。经 `validation/scan_cop_real_anchor_gap.py` 量化扫描后，这个说法**不准确**——详细数据见 `COP_REAL_ANCHOR_AUDIT_20260901.md`。
> 在与真实硬件容量与工况可比的点（18.8 kW @ 45 °C）上，补齐电机/变频损耗与风机泵功耗后模型 COP = 2.59，而同容量巴士空调实测 2.76，**模型反而低 6%**。制冷循环的物理内核是可靠的；真正的问题是**核算口径只到压缩机轴端**，漏了电机效率、变频损耗和冷凝风机三项。

## 6. 风险清单与技术债

按优先级排序：

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 1 | **能耗核算口径不完整**：`compressor_shaft_power_w` 只到轴端，缺电机效率、变频损耗与冷凝风机（模型里压根没有风机功率项），直接引用会高估 COP 约 1.3~1.6 倍 | `refrigeration.py` / `plant.py` | 高——影响任何能耗/COP 结论（物理内核本身可靠，见专项审计） |
| 1b | **压缩机效率图压比轴不覆盖运行区间**：图覆盖 4.0~10，实际运行在 1.90~3.44，全部靠 `np.clip` 钳到边界列，压比对效率的影响完全未被建模 | `refrigeration.py:36` | 中高——方向不明，需低压比样本数据才能定论 |
| 1c | **泵功率自相矛盾**：`power_w(2400)=5.9 W` 低于模型自身水力功率 22.1 W（隐含效率 375%）；管网阻力 39 kPa 比真实机组 160 kPa 低 4.1 倍 | `hydraulics.py` / `parameters.py` | 中——泵功耗被低估约 5 倍 |
| 2 | **架构声明被违反**：README 称"运行时不导入 legacy 单 Pack 项目"，但 `physics_p_nmpc_model.py` 通过 `sys.path` 注入父目录导入 `single_pack_plant` | `control/physics_p_nmpc_model.py:27-31` | 高——破坏模块独立性，部署时会踩坑 |
| 3 | **冻结工件校验器形同虚设**：覆写后校验只约束已弃用字段 | `physics_p_nmpc_model.py:186-190` | 中——工件损坏无法被自动发现 |
| 4 | **两代控制器并存**：`cluster_domp_*` 与 `chiller_surrogates` 已过时仍留在库内 | `control/` | 中——误导后续维护者 |
| 5 | **魔法数字**：`plant.py` 卸载回退里硬编码 `1000.0` 而非引用 `MINIMUM_COMPRESSOR_SPEED_RPM`；`COMPRESSOR_SPINUP_SPEED_RPM = 900` 与 1000 rpm 下限的关系靠注释维系 | `plant.py:366`、`plant.py:45` | 低——但改参数时易漏 |
| 6 | **跨延迟能量平衡未建模**：`cross_delay_energy_balance_is_modeled = False` | `plant.py:529` | 低——已知并显式标注 |
| 7 | **长时程偏差未评估**：>600 s 的模型-Plant 偏差尚无数据 | 报告第 5 节 | 中——决定能否用于长时仿真 |

### 一个容易被忽略的细节

`PUMP_VIRTUAL_SPEED_SCALE = 2.0`：泵在 Stage 8D4b 被放大 2 倍（参考流量 28 → 56 L/min），但冻结预测器是按老泵标定的。解法是让模型看"虚拟转速 = 实际转速 × 2"。**这是模型与设备代差的补丁，一旦有人动了泵参数而忘记同步这个系数，闭环会静默失准**——建议在代码里加断言或注释交叉引用。

## 7. 总体评价

**成熟度：高。** 这不是玩具代码。三个特征说明了这一点：能量守恒审计成体系、分级回归测试纪律严明、数值失效有物理意义的降级路径而非粗暴截断。

**当前阶段**：正处于"理论自洽已完成，开始对接真实设备"的转折点上。今日新增的真实数据锚点目录就是这个转折的信号弹。

**最该做的三件事**（按投入产出比排序，详见 `COP_REAL_ANCHOR_AUDIT_20260901.md`）：
1. **补核算口径，而不是改物理**。在 `ClusterPlantOutputs` 里新增 `electrical_power_w = shaft/η_drive + fan + pump`，保留原轴功率值以便追溯。零风险，且立刻让能耗结论可用——物理内核已被验证可靠，缺的只是口径。
2. **复核 NMPC 节能结论的口径**。RegD 工况的"−40% 节能"是按轴功率算的；计入固定风机功耗后会稀释到约 −29~−32%。对外汇报前必须换算。
3. **补全低压比效率数据再决定是否下修**。效率图压比轴（4~10）不覆盖运行区间（1.9~3.4）是确凿缺陷，但修正方向需要样本数据支撑，不宜凭推断下修。顺带修掉泵功率 >100% 效率的矛盾。
4. 清理 `control/` 的两代控制器，并在 `physics_p_nmpc_model.py` 里把对兄弟项目的依赖显性化（配置文件或依赖注入），消除 `sys.path` hack。
